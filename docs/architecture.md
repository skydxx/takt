# Рабочая архитектура продукта

Рабочее название: **Такт / Takt**. Название перед коммерческим запуском требует проверки домена, товарного знака и существующих продуктов.

## Целевой первый релиз

Сначала строим модульный монолит, а не набор микросервисов:

- `api` — FastAPI, авторизация, организации, ПВЗ, роли, подписки и финансовые данные;
- `web` — серверный кабинет владельца на Jinja/HTMX; меньше клиентского кода и проще E2E;
- `bot` — отдельный процесс aiogram, который использует тот же application/domain слой;
- `worker` — фоновые задачи: тревоги, отчёты, импорт и повторные попытки;
- `collector` — отдельный изолированный Playwright-воркер для кабинетов Ozon/WB;
- PostgreSQL — основная база в продакшене, SQLite допускается только для локальных тестов;
- Redis — очередь и распределённые блокировки, когда появится больше одного процесса;
- S3-совместимое хранилище — резервные копии и импортированные отчёты, без секретов в репозитории.

## Границы модулей

- `identity`: владелец, управляющий, сотрудник, приглашения, сессии, 2FA;
- `organizations`: организация, ПВЗ, Telegram-чаты и области доступа;
- `shifts`: открытие, передача, закрытие, ручная коррекция, журнал событий;
- `payroll`: ставки, видимость ставки, расчёт и блокировка исторических результатов;
- `subscriptions`: тариф, активные точки, период, grace period и напоминания;
- `finance`: доходы, расходы, импорт, P&L и источник каждого значения;
- `alerts`: постоянный инцидент неоткрытия, cooldown и идемпотентная доставка;
- `integrations`: Telegram Bot API, пользовательский Telegram caller и read-only collectors;
- `audit`: неизменяемый журнал действий и изменений прав/ставок/денег.

Модули не обращаются к таблицам друг друга напрямую. Сначала вызывается application-команда, а запись в базу выполняется через repository. Это нужно, чтобы бот, сайт и будущий мобильный API использовали одинаковые правила.

## Порядок миграции

1. Зафиксировать старое поведение и данные копии проекта.
2. Вынести чистые расчёты смен и денег в тестируемый domain-слой.
3. Создать новую схему PostgreSQL и импортёр старой SQLite-копии.
4. Поднять новый API рядом со старым Flask-приложением на staging.
5. Перенести сайт по экранам, начиная с onboarding и текущего состояния сети.
6. Переключить бот на новый application-слой.
7. Только после сверки удалить старые VPN-страницы и таблицы отдельной миграцией.

## Правила, которые нельзя нарушать

- Деньги и часы хранятся в целых минимальных единицах или Decimal, не в float.
- Все даты хранятся в UTC, отображение — Europe/Moscow.
- Смена и тревога имеют идемпотентный ключ.
- Ставка фиксируется в результате расчёта; изменение настройки не меняет прошлую зарплату.
- Ни один секрет не попадает в git, логи, ошибки или клиентский HTML.
- Любой импорт внешнего кабинета сначала сохраняется как сырьё, затем проходит проверку и только потом меняет P&L.

## Реализованный переходный слой

Пока legacy SQLite и Flask ещё не заменены полностью, новый кабинет использует
отдельный `platform_store.py` и таблицы с префиксом `platform_`. Это позволяет
выпустить рабочий onboarding без смешивания VPN-магазина и старых расчётов.

- код подключения выпускается вручную после оплаты и потребляется один раз;
- код может нести тарифный идентификатор и лимит активных ПВЗ; активация и продление применяют их атомарно;
- активация создаёт организацию, владельца, подписку на 30 дней и аудит-событие;
- владелец может добавить ПВЗ, пригласить управляющего/сотрудника и ввести доходы/расходы с агрегированным результатом по точке;
- доступ участника к ПВЗ хранится отдельной связью и проверяется при выдаче данных и финансовой записи;
- ставки точки и персональные ставки хранятся отдельно: владелец видит все, участник — общую и только свою персональную/скрытую ставку;
- приглашённый участник может создать аккаунт по одноразовой ссылке без кода владельца;
- команды смены, дни и точное время зарплатных уведомлений хранятся как настройки организации;
- состояние подписки пересчитывается из периода: `active` → трёхдневный `grace` → `expired`, а структурные записи после истечения блокируются;
- кабинет показывает дату окончания и остаток дней активного/grace-периода;
- настройки можно применить одним из пресетов или заменить полностью вручную.
- подключённый Telegram chat id связывается с конкретным ПВЗ, а бот читает
  команду открытия смены и интервал тревоги из настроек этой организации.
- при подключении через кабинет переходный bridge создаёт/обновляет запись
  чата в legacy DB; общая ставка синхронизируется с legacy hourly rate до
  полного переноса расчётов в platform-схему.
- окно работы точки хранится в `platform_points` и при bridge-подключении
  передаётся в `chat_settings`, включая ночной переход через полночь.
- кабинет читает выбранный из последних периодов расчёт смен только для видимых
  подключённых чатов; расчёт остаётся в legacy bot DB до завершения миграции payroll.
- по тому же периоду кабинет может показать отдельные смены, не изменяя legacy-записи.

Зарплатные и подписочные напоминания уже проходят через отдельный `worker.py`:
она учитывает период 1–15/16–конец месяца, роль, день и время из сценария,
проверяет привязанный Telegram ID и пишет идемпотентный журнал доставки в
`platform_notification_log`. Повторные попытки старых отчётов также больше не
являются заглушкой. Перед production всё равно нужны PostgreSQL и полноценная
identity-модель; worker-контур уже отделён от процесса команд бота.

Это переходный SQLite-адаптер. Перед production его нужно заменить PostgreSQL
repository с миграциями и вынести фоновые уведомления в worker.

Переходная SQLite-схема уже ведёт `platform_schema_migrations`: базовая версия
фиксируется при обнаружении старой базы, а текущая миграция добавляет поля чатов,
тарифа и переключатель регистрации сотрудников идемпотентно.

Целевая PostgreSQL-схема зафиксирована в
`migrations/postgres/001_platform_schema.sql`. Это DDL-контракт для будущего
repository: суммы хранятся в `BIGINT`-копейках, даты — в `TIMESTAMPTZ`, а
аудит/сценарии — в `JSONB`. Production DSN задаётся через
`PLATFORM_DATABASE_URL`; `platform_database.py` сохраняет единый DB-API слой
для текущих domain-методов и оставляет SQLite локальным fallback. Перед
переключением боевой базы importer `migrate_platform_sqlite_to_postgres.py`
делает dry-run и отказывается писать в непустую цель; затем нужны staging-сверка
и резервный план отката.

## Найденный разрыв со своим же правилом: float в legacy-боте

Правило "деньги и часы в целых минимальных единицах или Decimal, не в float"
(см. выше) соблюдается в `platform_store.py` (`amount_minor INTEGER`, копейки,
с проверками диапазона), но **не** в живой legacy-схеме `database.py`, которая
до сих пор считает реальную зарплату по чатам ПВЗ:

- `chat_settings.hourly_rate`, `member_rates.hourly_rate`/`custom_rate`,
  `salary_history.salary_amount`, `shift_records.earned_amount`/`hours_worked`
  — все объявлены `REAL`, т.е. IEEE-754 float.
- Пока payroll не перенесён на `platform_store`/PostgreSQL (см. "Порядок
  миграции" выше), это прямой источник накопительной ошибки округления в
  реальных выплатах, особенно при суммировании множества смен за период.
- Разовый безопасный фикс: перейти на копейки (`INTEGER`) или `Decimal`-текст
  для этих колонок при следующей миграции legacy-схемы, с явным round-trip
  тестом на существующих `salary_bot.db`/`platform.db` данных перед деплоем.
  Не делать это без миграции "на живую" — часть кода уже полагается на float
  сравнения/агрегации в SQL (`SUM`, `AVG`) для этих колонок.

## Telegram-звонки на пользовательской сессии: статус — 0%

`docs/product-vision.md` фиксирует решение делать звонки "отдельным сервисом
на пользовательской сессии, а не через Bot API". По состоянию на этот
аудит в репозитории нет ни одной зависимости userbot-библиотеки (`telethon`,
`pyrogram` и т.п.), ни кода, ни заготовки сервиса — только упоминание в
доке. Кто бы ни начинал эту работу, отправная точка — новый процесс/модуль,
а не что-то, что уже частично написано.
