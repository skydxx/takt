# Базовая модель безопасности

## Найденные риски старого прототипа

- секретные runtime-файлы лежат рядом с кодом и раньше не имели локального `.gitignore`;
- Flask secret key генерируется заново при каждом запуске, если переменная не задана;
- cookie `session_token` выставляется без явных `Secure` и `SameSite` флагов;
- POST-формы не имеют общего CSRF-механизма;
- SQLite-схема создаётся через `CREATE TABLE IF NOT EXISTS`, но не мигрируется;
- production systemd-сервисы запускаются от отдельного системного пользователя,
  а не от `root`; для них включены `NoNewPrivileges`, `ProtectHome` и
  `ProtectSystem=strict` с явным `ReadWritePaths` только для каталога приложения;
- production-конфигурация завершается с ошибкой без `PLATFORM_DATABASE_URL`,
  чтобы PostgreSQL не подменялся SQLite незаметным fallback;
- ответы на секретные вопросы используются только для проверки и не сохраняются
  в заявке на сброс пароля; администратору доступен только подтверждённый статус
  и контакт пользователя;
- одноразовые Telegram link keys хранятся только как SHA-256 digest, а их
  значения не попадают в логи бота;
- в одном файле смешаны доменные расчёты, SQL и старый VPN-магазин;
- глобальный список тревог хранится в памяти процесса и теряется при перезапуске;
- один старый модуль VPN был синтаксически невалиден и вынесен в `legacy/` без удаления.
- старый VPN-магазин оставлен в исходниках для миграции, но выключен флагом `VPN_ENABLED=0` по умолчанию.

## Обязательные меры новой версии

- отдельные секреты для development/staging/production;
- Argon2id или bcrypt с параметрами из конфигурации, без самодельного хранения паролей;
- короткие сессии, ротация, отзыв всех сессий и `HttpOnly`, `Secure`, `SameSite=Lax` cookies;
- CSRF для browser-сессий и проверка `Origin`/`Referer` для state-changing запросов;
- rate limit логина, регистрации, восстановления и Telegram link-кодов;
- rate limit подбора кодов активации и продления подписки по IP и identity;
- политика identity при регистрации: логин 3–64 символа из Unicode-букв/цифр и `._-`, пароль 12–256 символов;
- одноразовые приглашения владельца с TTL и однократным потреблением;
- владелец может отключить регистрацию по приглашениям; при отключении новые и ещё не принятые ссылки блокируются;
- RBAC с проверкой организации и ПВЗ на каждом запросе, не только в интерфейсе;
- журнал входов, изменений ставок, финансовых операций, прав и импортов;
- секреты коллектора в отдельном secret store; пароль маркетплейса не сохранять;
- внешняя нейросеть получает только минимальный очищенный фрагмент и только после согласия клиента;
- резервные копии шифруются до отправки в хранилище и регулярно проверяются восстановлением;
- безопасные заголовки, ограничение размера запросов, таймауты и понятные ошибки без traceback наружу.

В переходном кабинете структурные операции (ПВЗ, Telegram-чаты, приглашения,
сценарии и продление) теперь доступны только владельцу организации. Управляющий
может добавлять финансовые записи только по выданным ему ПВЗ, но не менять
структуру. Владелец может выдать или отозвать доступ к отдельной точке; это
фиксируется в аудите.

Финансовый CSV-экспорт использует ту же область видимости: управляющий получает
только записи доступных ему ПВЗ, а не весь набор организации.

Сводка payroll в кабинете доступна владельцу и управляющему; роль сотрудника не
получает общий список выплат коллег и не инициирует обращение к legacy payroll DB.
Payroll CSV использует то же ограничение: сотрудник получает HTTP 403.

Журнал аудита в кабинете доступен только владельцу и управляющему, содержит
только безопасные action/entity/metadata и не подставляет секреты в HTML.

Для переходного Flask-кабинета добавлено постоянное атомарное хранилище
`platform_rate_limits`: вход ограничен восемью попытками за 15 минут на IP и
логин, регистрация и восстановление — пятью за час, связывание и отвязка
Telegram — десятью за час. В базе сохраняется только SHA-256 ключа корзины, а не исходный
IP или логин. Перед production нужно вынести лимитер в Redis/PostgreSQL и
добавить очистку старых корзин.

GitHub Actions дополнительно проверяет отслеживаемые файлы на распространённые
паттерны Telegram/API-токенов перед публикацией сборки.

Веб-сессии больше не сохраняют cookie-токен в открытом виде: новые значения
хранятся как SHA-256 digest, а старые plaintext-записи мигрируют при инициализации
legacy DB.

Статистические запросы legacy-бота используют существующую колонку `salary_amount`
для пересчёта общей ставки; обращения к отсутствующей `daily_rate` удалены.

## Разрыв: 152-ФЗ и персональные данные

Продукт по конструкции обрабатывает персональные данные граждан РФ: ФИО,
телефон/Telegram-контакт сотрудников и управляющих, а также их зарплату/ставку
(регулярно фигурирует как "иные персональные данные" в реестре Роскомнадзора,
а не спецкатегория, но всё равно требует правовых оснований обработки). На
момент этого аудита в репозитории и доках нет ни одного упоминания 152-ФЗ,
политики конфиденциальности, основания обработки (согласие/договор) для
данных сотрудника/управляющего, ни явного подтверждения, где физически стоит
основная БД (ст. 18 ч.5 152-ФЗ требует локализации ПДн граждан РФ на
территории РФ для операций сбора). Согласие сейчас берётся только один раз —
в форме заявки на подключение на лендинге (`connect-form`, чекбокс
`field_consent`), и покрывает только лид/контакт по заявке, не последующую
обработку данных сотрудника внутри кабинета.

Это не блокирует текущую разработку, но перед коммерческим запуском нужно
закрыть отдельно от кода:
- подтвердить страну хостинга основной (не резервной) БД;
- опубличить политику конфиденциальности и основание обработки для
  владельца/управляющего/сотрудника (обычно — исполнение договора оказания
  услуг между Такт и владельцем, а не отдельное согласие сотрудника, но это
  решение юриста, не инженера);
- решить, нужна ли регистрация оператора ПДн в реестре Роскомнадзора.

## Изоляция операторской/админской поверхности: отдельные процессы, не флаг

Раньше `/admin*`, `/owner*` и `/backups*` жили в том же Flask-процессе, что и
публичный сайт, и были скрыты только декоратором `admin_host_required`
внутри одного приложения. Это было признано недостаточным: компрометация
процесса или простая ошибка в условии всё ещё давала доступ ко всей
admin-поверхности из одного и того же кода. Текущая архитектура — реальное
разделение на уровне процессов/контейнеров:

- **`web_app.py`** — публичное WSGI-приложение. Не импортирует
  `admin_routes.py`/`admin_app.py`, не знает про `ADMIN_HOST` (у модуля
  `web_app` нет такого атрибута — см.
  `tests/test_admin_host_isolation.py::test_public_app_does_not_know_about_admin_host`),
  не регистрирует ни одного `/admin*`, `/owner*`, `/backups*` маршрута.
  Запрос на эти пути отдаёт ровно тот же публичный 404, что и любой другой
  несуществующий путь (без редиректа на логин, без намёка на существование
  admin-поверхности) — см.
  `tests/test_admin_host_isolation.py::test_public_app_admin_owner_backups_paths_are_plain_404`
  и `test_public_app_404_for_admin_path_matches_generic_unknown_path_404`.
- **`admin_app.py` + `admin_routes.py`** — отдельное WSGI-приложение,
  отдельный процесс/порт (`ADMIN_WEB_PORT`, по умолчанию 5001), отдельные
  `db`/`platform_store` (свои Python-объекты `Database`/`PlatformStore`, не
  общие с `web_app.py` — см. "Разрыв" ниже), собственные `/login`/`/logout`
  (сессионная cookie не гарантированно долетает между разными доменами в
  реальном деплое, поэтому у admin-приложения свой вход, а не переиспользование
  публичной сессии). Здесь и только здесь применяется `ADMIN_HOST` — как
  defense-in-depth ВНУТРИ уже единственно-возможной точки входа на эту
  поверхность, не как единственная граница.
- **`core.py`** — общий, database-agnostic слой (`run_async`, кастомные
  404/403/405/500 страницы). Намеренно не хранит `db`/`platform_store` —
  каждое приложение открывает своё соединение к одному и тому же
  файлу/DSN, эмулируя реальный процесс-сплит уже сейчас.
- **Контейнеры.** `Dockerfile` (публичный) и `Dockerfile.admin` (админский)
  собираются из явного allow-list файлов, а не `COPY . .`: публичный образ
  физически не содержит `admin_app.py`, `admin_routes.py`,
  `backup_manager.py` и `templates/admin/` — это гарантия на уровне
  собранного образа, а не просто "код не импортируется". Пример топологии —
  `docker-compose.example.yml` и `deploy/nginx.example.conf`: единственный
  контейнер, опубликованный наружу — reverse proxy; `admin`-контейнер не
  публикует порт на хост вообще, до него можно дотянуться только из
  reverse proxy на общей docker-сети.

Модель угроз ADMIN_HOST-гейта внутри `admin_routes.py` (host-сравнение,
редирект/404, регистронезависимость и т.д.) не изменилась по сути — см.
`admin_host_required`/`_admin_host_response`/`_admin_host_matches` в
`admin_routes.py` — только переехала туда вместе с маршрутами:

- **Что это даёт.** Если `ADMIN_HOST` задан, запрос на эти маршруты с
  любого ДРУГОГО хоста не доходит до `render_template`: HTTPS-запрос
  получает редирект на `https://ADMIN_HOST<путь+query>`, запрос без HTTPS
  сразу получает 404. Сравнение хоста регистронезависимое, с раздельной
  проверкой порта и точным совпадением имени хоста (без substring/suffix).
  Цель редиректа всегда берётся из серверного конфига, никогда из
  `Host`-заголовка запроса — поэтому это не open redirect.
- **Что это НЕ даёт.** Ни домен, ни процесс-сплит сами по себе — не
  TLS-терминация и не firewall; их обеспечивает reverse proxy/сеть. Роли
  (`admin_required`/`super_admin_required`/ручные проверки) и CSRF остаются
  нетронутыми и продолжают проверяться после host-гейта, не вместо него.
- **Локальная разработка и тесты.** `ADMIN_HOST` пуст по умолчанию — все
  проверки хоста становятся no-op. `tests/test_admin_host_isolation.py`
  покрывает: route-separation на публичном приложении (7 тестов) и
  ADMIN_HOST-гейт на админском приложении (default-off, HTTPS-редирект с
  точной безопасной целью, HTTP→404, сохранение query string, точное
  совпадение хоста, регистр/порт, lookalike-хосты, сохранение роли на
  правильном хосте, покрытие ручных backup-роутов) — через
  `app.config`/`monkeypatch`, без реального DNS.
- **Кастомные страницы ошибок.** `core.register_error_handlers` регистрирует
  404/403/405/500 на обоих приложениях — статичный, самодостаточный HTML без
  Jinja-наследования (не может случайно подтянуть чужой sidebar/шаблонное
  состояние), без traceback/путей/секретов даже в production-режиме (когда
  `TESTING`/`DEBUG` выключены и Flask реально вызывает наши хендлеры, а не
  пробрасывает исключение). Публичное приложение локализует их через
  существующий RU/EN переключатель (`public_language`); админка — всегда
  RU. См. `tests/test_error_pages.py`.
- **Шаблоны.** Все 9 admin-only шаблонов (`admin.html`, `admin_users.html`,
  `admin_leads.html`, `admin_info.html`, `owner_dashboard.html`,
  `owner_vpn_orders.html`, `backups.html`, `backup_viewer.html`,
  `backup_chat_view.html`) живут в `templates/admin/` и наследуются от
  `templates/admin/base.html` (отдельного от публичного `templates/base.html`
  — публичный `base.html` не содержит ни одной ссылки на admin-only
  endpoint, только статичную информационную строку в навигации о том, что
  панель оператора вынесена на отдельный домен).

## Разрыв: общая БД между public и admin

Текущий сплит — реальное разделение процессов/образов/маршрутов/шаблонов, но
не полное разделение данных:

- оба приложения открывают одно и то же значение `DATABASE_PATH` (легаси
  SQLite) и один и тот же `PLATFORM_DATABASE_URL`/`PLATFORM_DATABASE_PATH` —
  разными объектами `Database`/`PlatformStore` в разных процессах, но по
  сути это общий файл/DSN на общем volume (`docker-compose.example.yml`,
  volume `takt-data`);
- Flask signing secrets теперь разные: `FLASK_SECRET_KEY` для public и
  обязательный в production `ADMIN_FLASK_SECRET_KEY` для admin;
- cookie имена тоже разные: public использует `session_token`, admin —
  `ADMIN_SESSION_COOKIE_NAME` (по умолчанию `admin_session_token`). Обе
  сессии всё ещё хранятся в общей legacy SQLite и проверяются по общей
  таблице, но cookie одного приложения не принимается другим;

Это осознанный, временный компромисс, а не недосмотр: следующий шаг —
разделение на уровне БД/API (отдельная read/write граница для admin, а не
прямой SQL-доступ к общей таблице), см. `docs/architecture.md`. До этого шага
компрометация общей БД затрагивает обе поверхности — процесс-сплит и разные
secrets защищают от компрометации кода/маршрутов или signing key одного
приложения, но не от компрометации общей инфраструктуры.

## Definition of done для production

Новая функция считается готовой только если есть миграция, unit-тесты domain-правил, integration-тест repository/API, Playwright E2E критического пути, аудит разрешений и проверка секретов.
